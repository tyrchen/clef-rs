# Metal and benchmark implementation evidence

Checked 2026-10-02 after the [existing Flash implementation evidence](clef-flash-implementation-research.md). The runner reports Apple M5 Pro (18 CPU cores, 20 GPU cores), macOS 26.5.2, and 64 GiB unified memory.

The published [Candle 0.11.0 Device API](https://docs.rs/candle-core/0.11.0/candle_core/enum.Device.html) has explicit Metal creation and synchronization. The locally inspected published Metal allocator clears unused buffers on synchronization, exposes current allocated/recommended working-set bytes, and uses a command queue with bounded compute encoders. Backend support does not qualify this model automatically: tiny backbone/head fixtures and full Flash weights are tested separately.

An initial GPU BF16-to-F32 weight conversion queued GPU work retaining temporary upload tensors and failed with a Metal out-of-memory callback on the full release. For Metal, bounded shard loading now converts the reviewed bytes on CPU before uploading their final dtype. This is weight preparation, not CPU inference fallback. CPU staging and GPU weights share physical RAM, so the Metal host planner includes both plus scratch/reserve; the OS-recommended GPU working set is checked separately.

The classifier head and vision tower are retained in F32 for the mixed Metal F16 profile; hidden states and selected lexical rows are promoted before the head. F32 residual additions, causal-convolution accumulation, query/key normalization, and beta sigmoid avoid repeated half-precision rounding; projection matmuls remain F16. Norms, tiled attention accumulation, decay, and recurrent state also use F32. The planner explicitly accounts for the additional promoted parameter bytes. A pure-F16 head experiment exceeded the CPU F32 probability gate. A later F16-vision asymmetric PNG case also exceeded it (0.001437 absolute probability error). These paths are not advertised; promoting the sensitive components preserves the original gate.

[Criterion 0.8.2](https://docs.rs/criterion/0.8.2/criterion/) is the latest stable version checked against official published documentation. It is a development-only dependency for repeatable domain microbenchmarks. Large-weight performance measurement uses a separate bounded harness because loading tens of GB, explicit cold/warm phases, fixed real request sizes, resource samples, admission failures and managed concurrency need richer accounting than a microbenchmark loop.

Normal inference synchronizes at completion. Diagnostic stage profiling adds barriers at backbone/head boundaries; its timings are labeled separately and are not used as the normal-path throughput estimate. CPU/Metal F32 is the same-precision comparison; Metal F16 is an explicit mixed-precision comparison with its own numerical evidence. No result combines simultaneously resident CPU and GPU models: backend processes run sequentially to avoid unified-memory contention.

The benchmark configuration now shares the server's bounded event preflight before `config` constructs a YAML tree. Inspection of the existing loader confirmed that YAML aliases clone referenced values, so byte caps alone do not bound expansion. The latest [yaml-rust2 0.13.0 event parser](https://docs.rs/yaml-rust2/0.13.0/yaml_rust2/parser/struct.Parser.html), published 2026-09-11, is used directly without encoding features; input has already been decoded as bounded UTF-8. The transitive loader version used by `config` remains independently guarded. Recorded inference measurements use the immutable executable from `0900a46`; the shared configuration preflight is outside the timed inference graph.

The completed campaign caught a memory-admission underestimate: Metal mixed F16 peaked at 26.661 GiB against an original 23.996 GiB estimate. Candle's queued temporary buffers are rounded and retained until synchronization. The final Metal planner budgets the largest FFN activation width rather than only the residual width, plus the existing 20% reserve and shard staging. Its 4,096-token text estimates are 28.796 GiB device / 39.944 GiB unified host for F16 and 49.828 GiB device / 60.977 GiB unified host for F32. A checked-in copy of the pinned model configuration is SHA-256-bound to the reviewed catalog in regression tests that cover both observed GPU peaks, text/image budgets and overflowing weight metadata. This changes admission arithmetic, not the measured tensor graph.

FP8 is not qualified or exposed by this version. The published dependency includes an `F8E4M3` storage type, but the [exact Candle 0.11.0 Metal matmul source](https://github.com/huggingface/candle/blob/31f35b147389700ed2a178ee66a91c3cc25cc80d/candle-core/src/metal_backend/mod.rs#L1730-L1754) accepts F32/F16/BF16 and rejects other dtypes. Supporting FP8 therefore requires a quantization/scaling and execution path, followed by independent numerical and performance qualification; adding a dtype enum variant alone cannot provide it. This is a limitation of the current execution path, not a statement that every Apple GPU lacks FP8 hardware capabilities.
